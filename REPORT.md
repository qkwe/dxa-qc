# Отчёт: контроль качества денситометрии (DXA) — что сделано, как и почему

## 1. Итог коротко

Готово работающее локальное ПО: читает DICOM (каталог или zip), сам группирует снимки
по исследованиям, определяет область и сторону, по каждому критерию ТЗ выдаёт решение
**с объяснением числом и порогом**, пишет таблицу xlsx/csv в формате ТЗ, дополнительные серии
(картинка с разметкой, DICOM Secondary Capture, DICOM SR), работает из командной строки,
через HTTP API и веб-интерфейс «в стиле АРМ». Ни один битый файл не роняет пакет.

Честная оценка (вложенная кросс-валидация по пациентам, тот же код, что в программе):

| Критерий | n / нарушений | AUC [95% ДИ] | F1 [95% ДИ] | Чувств. | Специф. |
|---|---|---|---|---|---|
| Позвоночник: некорректная укладка | 99 / 6 | 0.90 [0.68; 1.00] | 0.71 [0.33; 0.92] | 0.83 | 0.97 |
| Позвоночник: не выровнена ось | 99 / 10 | 0.85 [0.74; 0.94] | 0.36 [0.10; 0.62] | 0.40 | 0.91 |
| Позвоночник: посторонние предметы | 99 / 17 | 0.96 [0.91; 1.00] | 0.87 [0.73; 0.97] | 0.94 | 0.95 |
| Бедро: некорректная укладка (ротация) | 150 / 36 | 0.86 [0.78; 0.93] | 0.70 [0.55; 0.82] | 0.83 | 0.82 |
| Бедро: некорректная область интереса | 150 / 7 | 0.90 [0.70; 1.00] | 0.77 [0.31; 1.00] | 0.71 | 0.99 |
| **Все снимки: качественное / есть нарушение** | 249 / 73 | **0.83** [0.77; 0.89] | **0.76** [0.68; 0.84] | 0.84 | 0.85 |
| **macro-F1 по типам нарушений** | | | **0.68** | | |
| **`quality_prob` (вероятность нарушения)** | 249 / 73 | **0.84** [0.78; 0.89] | | | |

`quality_prob` — колонка из «Разъяснений V2» (вопрос 8), по ней организатор считает ROC-AUC. Вероятности
откалиброваны: в среднем 0.28 при доле брака 0.29. По одному `quality_class` (0/1) AUC был бы ~0.80.

Для сравнения — решение сокомандника, пересчитанное по той же честной схеме: AUC «есть
нарушение» 0.64, macro-F1 0.25 (в его отчёте 0.37 — из-за подбора порога на тех же данных).

## 2. Задача и данные

* ТЗ: поясничный отдел позвоночника (укладка — видны гребни подвздошных костей и половина Th12;
  ось — наклон ≤ 5°; нет посторонних предметов) и проксимальный отдел бедра (позиционирование,
  отсутствие ротации по малому вертелу, область интереса — 3 см сверху/снизу, 2 см сбоку).
* Набор: 100 исследований, 499 файлов, **252 уникальных снимка** (позвоночник 99, бедро 153),
  один аппарат GE Lunar Prodigy Advance, 8 бит, ~300×300 пикселей.
* Нарушений очень мало: 6 / 10 / 17 на позвоночнике, 36 / 7 на бедре.

Отсюда главный принцип решения: **нейросеть учить не на чем, поэтому то, что ТЗ задаёт
числом, мы меряем, а обучаем только то, что формулой не описать.** Измерение объяснимо врачу,
проверяемо (повернули снимок на 7° — сервис показал 7°) и не переобучается.

## 3. Как устроено решение

```
DICOM (каталог/zip) → чтение и дедупликация копий → группировка по StudyInstanceUID
  → область: теги/имя файла, иначе ширина снимка (позвоночник 300 пикселей, бедро 248–280)
  → сторона бедра: теги/имя (ЛПОБ/ППОБ), иначе анатомия (головка и таз медиально)
  → измерения по критериям ТЗ (dxa/axis, spine, roi, rotation)
  → решение по каждому критерию (dxa/model.py) → таблица + доп. серии
```

| Критерий | Решение | Обучаемые параметры |
|---|---|---|
| Ось позвоночника | правило ТЗ: угол линии через центры крайних позвонков > 5° | нет |
| Укладка позвоночника | правило ТЗ: гребней подвздошных костей не видно (кости по бокам у нижнего края < 0.5%) | нет |
| Посторонние предметы | гессиановый детектор тонких ярких линий вне столба и поверх него | два порога |
| Область интереса бедра | правило ТЗ: от малого вертела до нижнего края < 3 см | нет |
| Укладка/ротация бедра | среднее двух процентилей: малый вертел (U-образно), офсет головки; седалищная кость в кадре | медиана, порог |

Итог по снимку — «есть нарушение», если сработал хотя бы один критерий; несколько нарушений
перечисляются все (мультилейбл), каждое со своим объяснением.

## 4. По критериям: что сделано и почему

### 4.1. Ось позвоночника (без МЛ)

* **Как меряет врач** — рис. 2 ТЗ: линия через центр нижнего и верхнего позвонков против вертикали.
  Мы строим среднюю линию столба (центр между краями столба в каждой строке, динамическое
  программирование против скачков) и берём **ту же двухточечную линию**.
* **Точность:** 594 поворота снимков на известный угол — средняя ошибка **0.19°** (95-й перцентиль 0.56°), 100% проверок в допуске ТЗ 3°.
* **Почему F1 невысокий при AUC 0.85:** врачи размечали на глаз. Правило ТЗ совпадает с врачом
  на 85 снимках из 99; 6 из 10 нарушений имеют наклон 2–4.6° (визуально прямой столб), а 8 «норм»
  наклонены больше 5°.
  Разметка расходится с порогом ТЗ **в обе стороны**, поэтому порог под разметку не подгоняем:
  выдаём угол и решение по ТЗ. Примеры строит `experiments/make_slides.py`.
* Порог, подобранный по данным (внутри фолдов), даёт F1 0.37 — не лучше порога ТЗ (0.36):
  5° из ТЗ оптимален и для этой разметки.
* Проверена идея «врач отмечает пациента, лежащего наискосок» — добавить смещение верхней части
  столба от центра кадра: F1 0.36 → 0.50, но AUC не вырос (0.84 против 0.85) — прирост от подгонки
  порога на 10 примерах, а не от лучшего ранжирования. Отклонено как вероятный шум и отход от ТЗ.
* SigLIP на этом критерии бесполезен (AUC 0.42) — угол не «видится» признаками общей модели.

### 4.2. Укладка позвоночника (без МЛ)

* ТЗ: внизу должны быть видны верхние края подвздошных костей. На всех снимках-нарушениях,
  кроме одного, кадр обрезан снизу, и «крыльев» гребней нет вообще (доля кости = 0).
* Правило «гребней не видно» (кость по бокам от столба в нижней четверти кадра < 0.5%):
  **5 из 6 нарушений при 3 ложных тревогах из 93**, AUC 0.90. Шестой случай, по-видимому,
  связан с верхней границей (Th12) — один пример, отдельное правило не строили.
* SigLIP даёт 0.79, вместе с правилом 0.91 — прирост в пределах шума при 6 примерах,
  предпочли прозрачное правило.

### 4.3. Посторонние предметы (детектор по зонам: мягкие ткани, поверх таза, поверх позвоночника)

* Что это в данных: в основном косточки бюстгальтера (тонкие очень яркие дуги сверху, ровно
  как рис. 3 ТЗ), скобы, металл. Трудность — рёбра и края костей тоже дугообразные.
* Детектор: собственное число гессиана на масштабе 1 пиксель (тонкие яркие гребни) вне
  позвоночного столба, 99.5-й перцентиль; порог — по обучающим данным.
* **Разбор ошибок (29.09) и три исправления механизма:**
  1. нули поля дополнения по краям кадра попадали в перцентиль и размывали его по-разному на
     каждом снимке — исключены (AUC 0.83 → 0.91);
  2. большинство ложных тревог — края гребней подвздошных костей: таз исключается из зоны поиска;
  3. таз ищется только вне столба — иначе позвоночник склеивал с тазом рёбра и лежащие на них
     косточки белья, и они терялись (найдено на тестовом фрагменте организатора).
* Итог тогда: AUC 0.95, F1 0.76 (было 0.83 / 0.51), найдено 14 из 17 при 5 ложных тревогах.
* **Четвёртое исправление (19.10, по рамкам на картинке).** Когда в интерфейсе появились рамки «где
  детектор увидел предмет», на нормальном снимке рамка встала на край гребня подвздошной кости: таз
  не отделился выше, и его край попал в зону поиска. Теперь сбоку не ищем в нижней четверти кадра —
  той же зоне гребней, что и для укладки. Вложенная CV: **AUC 0.962, F1 0.889** (чувств. 0.94,
  специф. 0.96; было 0.946 / 0.757, 0.82 / 0.93); одинаково при исключении 15–30% высоты, взята
  анатомическая зона 25%, а не лучшая точка. Цена — предмет на тазу перестал искаться; это закрыто
  следующим пунктом.
  Оговорка: четыре итерации на тех же 99 снимках — возможен небольшой оптимизм; все правки
  исправляют механизм (что попадает в зону поиска), пороги не подгонялись.
* **Предметы, наложенные на кость (замечание экспертов 16.10: исключать их нельзя), 20.10.**
  Проверили количественно — стендом `validate_foreign_object.py`: 21 настоящий предмет (косточки,
  застёжки) вырезан с размеченных снимков и перенесён на нормальные снимки в три зоны; металл добавляет
  ослабление к фону, затем снимок нормируется как у аппарата. Детектор обучается на одной половине норм,
  проверяется на другой. Прежняя версия находила поверх таза 8%, поверх позвоночника 5% — то есть была
  к ним слепа (детектор «r1 − r3» внутри столба на реальных снимках не срабатывал ни разу).
  Сравнили 11 признаков для зон на кости (тонкая линия, «ярче медианы окружения», top-hat, насыщение,
  симметрия столба, сравнение с соседними позвонками по идее SQUID, их сочетание логрегрессией на синтетике).
  Взят отклик тонкой яркой линии, усреднённый по окну 5 пикселей, максимум по зоне; у каждой зоны свой
  порог — максимум по нормам обучающей части × 1.02. Итог на отложенных нормах: **поверх таза 96%,
  поверх позвоночника 16%, мягкие ткани 67%, ложные тревоги 6%**. Реальная CV: предметы F1 0.889 → 0.865
  (одна лишняя тревога на 82 нормы) — плата за то, что сервис перестал быть слепым к предметам на тазу.
  Позвоночник — честное слабое место: замыкательные пластинки позвонков дают тот же отклик, что тонкий
  металл; лучший из 11 вариантов — 38%. Открытых размеченных наборов DXA с предметами нет (проверено);
  ближайшие — рентген грудной клетки (Hopkins RFO, Object-CXR) — задел на будущее.
* **Находка в разметке:** нормальный по разметке снимок `4101816664` содержит хорошо видимую косточку
  белья вверху кадра (выше L1). Либо ошибка разметки, либо врачи не считают нарушением предмет вне
  зоны анализа L1–L4 — вопрос экспертам; от ответа зависит, где искать предметы.
* Не ловим: «выраженные наложения» без видимого предмета (газ, кальциноз аорты) — субъективная часть критерия.
* SigLIP на этом критерии хуже (0.65). Локальная VLM (Qwen3-VL-2B, `experiments/vlm_probe.py`) не проверена —
  веса не скачались; API-VLM запрещены ТЗ (медданные наружу).

### 4.4. Область интереса бедра (без МЛ)

* Рамки области интереса GE в выгрузке **нет** — строим её по ориентирам: головка (карта
  расстояний, не ближе 25 мм медиальнее оси диафиза), малый вертел, большой вертел.
* **Буквальное правило 3/3/2/2 от анатомии не работает:** срабатывает на 135 нормах из 143.
  Большой вертел почти всегда у края кадра, у половины норм головка ближе 3 см к верху —
  рамка GE, от которой считает ТЗ, уже анатомии.
* Однозначно меряется **отступ ниже малого вертела**: правило ТЗ «< 3 см» — 3 из 7 нарушений
  без единой ложной тревоги. Остальные отступы выводятся в отчёт как информация.
* **Второе правило (29.09) — длина скана < 13 см.** Разбор пропусков: два нарушения — кадры, где
  бедро почти не попало в снимок (поле 12.4–12.7 см). Из ТЗ: стандартная область интереса бедра
  ~7 см + по 3 см сверху и снизу = минимум 13 см. Порог 12.5 / 13 / 13.5 даёт одно и то же — не подогнан.
  Итог: **5 из 7 при 1 ложной тревоге** (этот снимок врач всё равно отметил браком по укладке),
  **AUC 0.90, F1 0.77** (было 0.81 / 0.60).
* Не ловим 2 нарушения — по измерениям неотличимы от норм.
* **Рамка при ненадёжных ориентирах (доработка после встречи 16.10).** На коротком скане
  (поле < 13 см) рамка области интереса ошибочно сегментировала посторонние структуры, и по ней
  нельзя было делать вывод. Теперь `roi.landmarks` возвращает флаг надёжности: при коротком скане
  или головке за кадром рамка на оверлее не рисуется (показывается причина), а решение принимается
  только по длине скана. Затронуто 5 снимков набора; метрики не изменились.
* Точность отступов (обрезка кадра на известные 0.5–2 см): отступ снизу — средняя относительная ошибка 2.3% (86% проверок в допуске ТЗ 5%), сверху — 1.3% (95%).

### 4.4a. Видимость структур бедра и позвоночника (проверено, частично принято)

* **Седалищная кость (ТЗ: «представлены большой вертел, шейка бедра и седалищная кость»)** —
  добавлено правило: кость в зоне медиальнее и ниже головки почти отсутствует (< 2%) → нарушение
  укладки. На данных: 1 нарушение, 0 норм. Метрик не меняет (случай ловился по ротации), но
  требование ТЗ теперь проверяется явно.
* **Большой вертел** — отдельно не проверяется: у нормальных снимков он почти касается края
  кадра, врачи за это не штрафуют.
* **Верхняя граница позвоночника (половина Th12)** — **не реализовано, осознанно.** Признак
  «видны 12-е рёбра» не работает: рёбер вверху не видно у 12–16 нормальных снимков из 93
  (12-е рёбра короткие и на DXA часто не видны). Честно — только подсчётом позвонков от крестца,
  а в разметке всего одно такое нарушение — проверить нечем. Названо ограничением.

### 4.5. Укладка и ротация бедра (измерения)

Самый частый вид брака (36 из 150) и самый трудный. Итог **AUC 0.86, F1 0.70** из двух независимых
измерений, веса равные, заданы заранее:

1. **Малый вертел — U-образно.** ТЗ: при переротации контур гладкий, при недоротации вертел
   слишком большой. Меряем площадь выступа медиального контура ниже шейки над локальным
   трендом. Зависимость действительно U-образная:

   | выступ | доля брака |
   |---|---|
   | маленький (гладкий контур) | 45% |
   | средний | 5% |
   | большой | 39% |

   Оценка — расстояние от медианы нормы (медиана считается только на обучающей части), **в
   логарифмической шкале** (29.09): площадь — величина «во сколько раз», и гладкий контур 1 мм²
   отличается от нормы 6 мм² так же сильно, как крупный вертел 36 мм². В линейной шкале
   переротация недооценивалась — большинство пропусков были как раз с выступом 1–3 мм².
   Ротация целиком: AUC 0.83 → **0.85**, F1 0.54 → **0.63**, найдено 25 из 36 вместо 20 при том же
   числе ложных тревог. Раньше признак «не работал» (AUC 0.5), потому что ждали монотонной связи.
   Проверена и отклонена отбраковка «невозможного» офсета (< 25 или > 75 мм как сбой измерения):
   AUC падает до 0.80 — сбой ориентиров сам несёт сигнал (у плохо уложенного бедра они ищутся хуже).

   **Что на самом деле меряется (проверено 19.10 по замечанию на защите прототипа).** Наибольший
   выступ ищется на всём медиальном контуре от шейки до диафиза. На сводке из 20 бедер у части
   снимков он приходится на сам малый вертел (переход шейки в диафиз), у части — на изгиб у шейки,
   где контур подходит к седалищной кости. Попробовали искать строго малый вертел, исключая верх
   участка: исключение 15 / 25 / 35 / 50% снижает ротацию AUC 0.863 → 0.851 / 0.840 / 0.815 / 0.736
   (вложенная CV). Значит, полезный сигнал — форма всего медиального контура шейки и диафиза, а не
   только вертел; измерение оставлено. На картинке это показано честно: жёлтая линия — анализируемый
   контур, кружок — «наибольший выступ контура» (только если ≥ 1 мм), иначе «контур гладкий».
2. **Офсет головки** (расстояние от центра головки до оси диафиза): при наружной ротации шейка
   в проекции укорачивается, головка ближе к оси — 41 мм против 48 мм у нормы. AUC 0.71.
3. **SigLIP-so400m убран (29.09).** Замороженная модель + логрегрессия на 16 главных компонентах
   сама по себе даёт AUC 0.70, и сигнал настоящий (перестановочный тест: на шуме 0.49 ± 0.08,
   p ≈ 0.01). Но как третья оценка к двум измерениям она **мешала**: ротация без неё AUC 0.852 → 0.863,
   F1 0.63 → 0.70, «есть нарушение» по бедру F1 0.68 → 0.75, по остальным критериям без изменений
   (та же честная CV). Её информация в основном уже содержится в измерениях, а своя ошибка
   добавляется. Попутно ушли torch, transformers и 1.6 ГБ весов: образ стал в несколько раз меньше,
   модель — 5 КБ, GPU не нужен ни при каком объёме. Область без тегов теперь определяется по ширине
   снимка (у аппарата организатора позвоночник всегда 300 пикселей, бедро 248–280; 252 из 252) —
   это настройка под один аппарат, что названо ограничением в разделе 9.

## 5. Протокол честной оценки

* Разбиение **по исследованию** (StratifiedGroupKFold): снимки одного пациента не попадают
  одновременно в обучение и проверку. 5 фолдов × 5 повторов.
* **Всё обучаемое — внутри фолда:** пороги (по F1 на out-of-fold предсказаниях обучающей
  части), медиана малого вертела, эталоны для процентилей, калибровка вероятностей.
* Число эпох/лучшая эпоха по тесту не выбираются (у нас нет эпох; при дообучении SigLIP в
  Colab эпохи фиксировались заранее).
* 95% ДИ — бутстрэп **по исследованиям**, а не по снимкам (снимки пациента зависимы).
* Контроль утечек: перестановочный тест (см. 4.5).
* Оценка выполняется **тем же кодом**, что в программе (`dxa/model.py`), — `evaluate_final.py`.

## 6. Находки в данных (важно для защиты)

## 8. Программное решение

* **Командная строка:** `python -m dxa.predict --input <каталог|zip> --output results.xlsx --series series/`.
* **API и веб-интерфейс:** FastAPI (`dxa/api.py`), загрузка zip/DICOM, фоновые задания,
  скачивание xlsx/csv/series.zip, просмотр снимка с разметкой и заключения. Оформление — в духе
  привычного АРМ (серые окна, синие заголовки, плотный журнал, строка состояния).
* **Доп. серии:** PNG и DICOM Secondary Capture с разметкой (ось, зона гребней, область интереса,
  головка; красное — нарушение), DICOM Basic Text SR с заключением по каждому критерию.
* **Устойчивость:** прогон всего обучающего набора как «чужих» данных (499 файлов + пустой,
  мусорный и обрезанный файлы): 499 Success, все 3 плохих файла — Failure с понятной причиной,
  247 копий распознаны; сторона бедра по анатомии (без обучения и без подсказок в именах файлов)
  верна в **153 из 153**; область по ширине снимка — в 252 из 252; на тестовом фрагменте область
  и сторона совпали с именами файлов ПОП/ЛПОБ/ППОБ. Дымовые тесты `tests/` проходят.
  Служебные DICOM без изображения (SR, DICOMDIR) пропускаются.
* **Скорость:** CPU (ноутбук): медиана 0.03 с на снимок, максимум 0.15 с; весь обучающий набор
  (499 файлов, 100 исследований) — 21 с при лимите ТЗ 3 мин на исследование. Загрузка модели ~2 с.
  До отказа от SigLIP было ~2 с на снимок и ~10 с загрузки.
* **Контейнер:** `Dockerfile` (python:3.10.16-slim-bookworm, все версии зафиксированы, модель
  внутри образа — работа без сети, GPU не нужен), `run.sh` (build / predict / api).
  **Образ собран и проверен** (Docker Desktop, 29.09, после отказа от SigLIP): **752 МБ** вместо 5.4 ГБ;
  пакетная обработка тестового фрагмента в контейнере **без сети** (`--network none`) даёт те же
  решения, вероятности и тексты объяснений, что и локальный прогон; API в контейнере — загрузка,
  задание, xlsx, csv, series.zip и веб-интерфейс отвечают 200. Пути к входу/выходу лучше брать
  без кириллицы (особенность WSL, на Linux-сервере это не проблема).

### 8.1. Настройки контроля (гибкость без переобучения)

Клиника может работать в другой точке «чувствительность — специфичность», на другом аппарате
или проверять не все критерии. Поэтому всё, что не требует переобучения, вынесено в настройки
(`dxa/settings.py`): файл JSON для сервиса (`./run.sh api my.json`, `--config`), переопределение
на каждое задание в API и панель «⚙ Настройки» в веб-интерфейсе.

* **Режим обучаемых порогов** (посторонние предметы, ротация бедра): `balanced` — максимум F1
  (умолчание); `sensitive` — порог, при котором на обучении находится ≥ 90% нарушений;
  `specific` — ≤ 5% ложных тревог. Пороги всех режимов подбираются внутри обучения и упорядочены
  (sensitive ≤ balanced ≤ specific). В интерфейсе у каждого режима — честные цифры с кросс-валидации:

  | Режим | «Есть нарушение»: чувствительность [95% ДИ] | специфичность [95% ДИ] | F1 |
  |---|---|---|---|
  | `sensitive` | 0.85 [0.78; 0.93] | 0.72 [0.64; 0.79] | 0.67 |
  | `balanced` | 0.84 [0.76; 0.91] | 0.85 [0.79; 0.91] | 0.76 |
  | `specific` | 0.59 [0.48; 0.70] | 0.91 [0.87; 0.95] | 0.66 |

  **Находка:** режим «высокая чувствительность» почти не поднимает общую чувствительность (0.84 → 0.85)
  ценой заметной потери специфичности. Пропуски брака в основном у оси позвоночника (чувствительность
  0.40), а там порог задан ТЗ — 5°, режимы его не трогают. Ротация бедра в `sensitive`: 0.83 → 0.89
  при специфичности 0.82 → 0.61. Поэтому по умолчанию остаётся `balanced`, а `sensitive` — для
  скрининга, где ложная тревога дешевле пропуска.
* **Пороги ТЗ** (5°, 3 см) и служебные пороги (13 см, доли кости) можно изменить, но каждое
  изменение помечается в заключении «[изменено пользователем; ТЗ: 5]», пишется в колонку `settings`,
  на лист `settings` в xlsx, в `settings.json` и в DICOM SR — результат остаётся воспроизводимым.
* **Отключение критериев** — например, если клиника проверяет седалищную кость вручную; отключённый
  критерий не выдаёт нарушений и не входит в `quality_prob`.
* **Аппарат:** `pixel_spacing_mm` — принудительный размер пикселя (ответ на открытый вопрос
  0.6 × 1.05 мм: если организатор подтвердит, это одна строка в настройках, без правки кода);
  `spine_min_width_px` — правило области для снимков без тегов.
* `quality_prob` от настроек не зависит: вероятности откалиброваны по разметке, поэтому ROC-AUC
  у организатора не меняется. Проверено: при настройках по умолчанию все 499 ответов и тексты
  заключений на обучающем наборе дословно совпадают с версией до доработки, метрики — тоже.

### 8.2. Исправлено при доработке

* **Загрузка через API затирала одноимённые файлы.** Имя бралось без подкаталогов, а выгрузки PACS
  часто называют снимки одинаково (`IM0001` в каждом исследовании) — из трёх таких снимков
  обрабатывался один. Теперь подкаталоги сохраняются, дубликаты имён получают суффикс, `..` и
  абсолютные пути отбрасываются. В интерфейсе добавлена загрузка папки целиком.
* **`/api/jobs/path` читал любой каталог сервера.** Теперь только каталоги из `DXA_INPUT_ROOTS`
  (в образе — `/data`), иначе 403.
* **Задания терялись при перезапуске сервиса** — ссылка `?job=<id>` переставала работать. Теперь
  состояние задания сохраняется в `job.json`.
* **Несуществующий вход в CLI** давал пустую таблицу и код 0 — теперь сообщение и код 2.
* В DICOM SR область писалась как `spine`/`femur` — теперь по-русски, со стороной и тем, как определена.
* **Область снимка нестандартного размера угадывалась.** Правило «шире 290 пикселей — позвоночник»
  верно только для «родных» снимков аппарата организатора. При проверке на скриншоте всё оказалось
  «позвоночником»: в сервис загрузили его же `series.zip`, где картинки с разметкой увеличены ×3.
  Теперь: теги/имя файла → правило ширины только для ширины 240–320 пикселей → иначе анатомия
  (`dxa/region.py`, логрегрессия на 6 масштабно-инвариантных признаках: симметрия, яркий столб по
  центру и его устойчивость по высоте, перекос яркости; 248 из 252 на кросс-валидации, все ошибки
  неуверенные). Увеличенные ×3 и уменьшенные ×0.5 копии тестовых снимков без подсказок — 6 из 6
  (старое правило — 3 из 6). На исходных снимках ответы не изменились (499 из 499).
* **Снимки другого разрешения мерились неверно** (найдено на копиях ×3 и ×0.5 тестовых снимков).
  Проверка правдоподобия тега (0.4–1.0 мм) отбрасывала настоящие 0.2 и 1.2 мм и подставляла 0.6 —
  все сантиметры ошибались в разы: на копии ×3 наклон 5.9° вместо 2.1°, на копии ×0.5 «короткий
  скан», косточка белья «поверх столба» (зона столба считается в мм). Кроме того, фильтры детекторов
  работают в пикселях родного разрешения. Теперь тег принимается в 0.1–1.5 мм (мусор тега в наборе —
  нули и 1.73 мм — по-прежнему отбрасывается), а снимок с пикселем вне 0.4–1.0 мм пересчитывается
  к 0.6 мм перед измерениями. Копии ×3 и ×0.5 дают те же вердикты, что оригиналы (тест), на исходных
  снимках ответы не изменились (499 из 499).
* **Наши доп. серии принимались за снимки.** DICOM SC с разметкой (Manufacturer «DXA-QC») теперь
  отклоняется с понятной причиной.
* **Разметка на картинке:** в окне просмотра подписи «рассыпались» — картинка уменьшалась без
  сглаживания (`image-rendering: pixelated`, годится только для увеличения); подпись угла оси
  пряталась под легендой; точка «малый вертел» бралась по краю всей маски кости и могла оказаться
  на тазу. Теперь уменьшение плавное, по щелчку — полный размер; угол подписан у середины линии;
  вместо «точки малого вертела» — анализируемый медиальный контур и его наибольший выступ (как в
  `rotation.py`, см. 4.5); у гладкого контура точка не рисуется — «контур гладкий, вертел не выступает».
* **Ночная проверка 20–21.10 (строгий аудит по ТЗ и разъяснениям):**
  * разделитель нарушений — «;» без пробела, буквально по «Разъяснениям V2» (вопрос 6);

### 8.3. Остановка, проверка для организаторов, инструмент врача

* **«■ Остановить»** прерывает загрузку (виден процент) или обработку на сервере
  (`POST /api/jobs/{id}/cancel`): текущее исследование дорабатывается, отчёт по обработанным сохраняется.
* **`./run.sh check <НД_для_обучения> [<Для_теста>]`** (`verify.py`) — проверка всего решения с нуля без
  участия команды: обучение и сверка с поставленной моделью (совпадает полностью), метрики CV с 95% ДИ,
  поверка измерителя, стенд предметов, пакетная обработка и проверка выдачи по ТЗ 2.5 и «Разъяснениям V2»
  (колонки, допустимые значения области и нарушений, разделитель, `quality_prob` в [0;1], время). Итог —
  `verification/verification.md`; все 15 проверок пройдены. Страница «Метрики» (`/metrics`) — то же в таблицах.
* **Инструмент врача** (`/review`) закрывает пункт ТЗ 2.6 «...с возможностью подтверждения специалистом»:
  врач подтверждает или исправляет заключение по каждому критерию и может обвести пропущенный предмет;
  исходный DICOM и метки уходят в набор дообучения. «Дообучить» — та же вложенная CV на наборе
  «организатор + врачи», сравнение с действующей моделью и согласие с врачами на их снимках. Новая
  модель — только кандидат: «Применить» (прежняя сохраняется) и «Откатить» — явные действия, иначе
  одна ошибочная пометка могла бы испортить сервис. Проверено полным циклом; на нарочно ошибочных
  метках кандидат оказался хуже (F1 0.72 против 0.76) — и это сразу видно в сравнении до применения.

## 9. Ограничения и риски на закрытом тесте

* Другой аппарат (Hologic и др.): правила в градусах и сантиметрах переносимы; пороги детектора
  предметов и оценки ротации могут потребовать перенастройки (`train.py` на новых данных), а правило
  области по ширине снимка — замены (при наличии тегов/имён файлов область берётся из них).
* Мало нарушений → широкие ДИ; особенно область интереса (7) и укладка позвоночника (6).
* Масштаб берётся из Exposed Area с проверкой правдоподобия; если тег неверен и правдоподобен —
  ошибка в сантиметрах.
* Если бедро почти не попало в кадр, ориентиры ненадёжны.
* Сторона бедра по анатомии проверена на 153 снимках обучающего набора и 2 тестовых (без ошибок).
* `quality_prob` = 1 − Π(1 − pᵢ) предполагает независимость критериев; на практике нарушения
  одного снимка могут быть связаны (плохая укладка → и ось, и гребни), тогда вероятность завышена.
  Ранжирование (ROC-AUC) от этого не страдает, калибровка в среднем верна (0.28 при доле брака 0.29).
* Посторонние предметы на кости: по стенду поверх таза находится ~96%, поверх позвоночника ~16% (4.3);
  реальных примеров на кости в наборе нет, оценка — по настоящим предметам, перенесённым на нормы.
* Организатор указал пиксель 0.6 × 1.05 мм, мы считаем его квадратным ~0.6 мм (головка бедра круглая,
  совпадение с разметкой); если на закрытом тесте это важно — одна строка настроек `pixel_spacing_mm`.

## 10. Как воспроизвести

```bash
python train.py --data <НД_для_обучения>                 # модель → models/quality_model.joblib
python evaluate_final.py --data <НД_для_обучения>        # честные метрики → out/metrics_final.json
python validate_measures.py --data <НД_для_обучения>     # поверка измерителя → out/validation.json
python validate_foreign_object.py --data <НД_для_обучения> # стенд предметов на кости → out/foreign_stand.json
python verify.py --data <НД_для_обучения> --test <Для_теста>   # всё сразу → out/verification.md
python -m dxa.predict --input <Для_теста> --output out/test_run/results.xlsx --series out/test_run/series
python -m dxa.predict --input <Для_теста> --output out/test_s/results.xlsx --mode sensitive   # другой режим
python -m pytest tests -q                                 # тесты
uvicorn dxa.api:app --port 8000                           # веб-интерфейс
```

`out/metrics_final.json` и `out/validation.json`, что приведены в отчёте. Исследования — `experiments/README.md`.
